# Clerk development-handshake defect on plsvc browser pages (2026-10-15)

Found on the owner's phone during the 9610 new-customer walk: the activation link `/go/<nonce>` showed a Clerk `host_invalid` error page instead of the setup page.

- **Cause.** The plsvc images v21-v23 were built with the Clerk publishable key that the build step read from the public home page of `bff.epic.dm`. After the host move that page is the host04 bff-v2, which publishes the Clerk DEVELOPMENT instance (frontend host `synthetic-staging.clerk.accounts.dev`). The production instance's frontend host is `clerk.epic.dm` (decoded host only, read from the stopped deepseek bff-v2 build env; no secret read). With a development instance, `clerkMiddleware` answers every real-browser navigation (`Sec-Fetch-Dest: document`) with a 307 to that instance's handshake endpoint, which fails on our domain. Plain curl never sends those headers, so no earlier check saw it.
- **Fix.** `middleware.ts`: add `/go/`, `/join`, `/call-dominica`, `/api/lite/` to `CLERK_BYPASS_PREFIXES`. All were already in `isPublicRoute`; none reads a Clerk session (Codex enumerated every route under `app/api/lite`). Image `localhost:5000/pl/plsvc@sha256:f313649f...` (full digest in the cutover transcript and in Port). Rollback: `REVERSE=1 NEW_IMAGE=<that digest> python scripts/owner-run/zz-plsvc-clerk-bypass-cutover.py` (returns to image b6e4c0bc, env untouched).
- **Verification.** `browser-replay.sh` replays real navigation headers: `/go/<nonce>` and `/go/back` return 200 with no handshake; `/api/lite/acrobits/tab-entry` returns 403 without credentials; CONTROL `/dashboard` and `/sign-in` still handshake (the probe can see one). The owner's line then registered at 11:51:43Z.
- **Not fixed here.** `/join`, `/dashboard` and `/sign-in` are served by the host04 bff-v2 (the router sends only `/api/lite`, `/api/internal/personal-line`, `/api/internal/payment-link` and `/go` to plsvc), which has the same development instance. Separate decision.
- **Lesson.** The build step must not take its publishable key from a page whose own build it does not control, and a browser-only failure needs a browser-header probe, not curl.
