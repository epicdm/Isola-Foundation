## RECOVERY: ONE RECORDED ESCALATION, NEVER RE-DRIVEN (permanent for this slice)
**Recovery no longer resumes a delivery. A delivery it cannot prove complete gets exactly ONE recorded escalation to a person; resumption is revisited only after fenced leases are authorised AND proven on a real PostgreSQL.**
- Why: four review rounds in a row found new defects in the recovery path that tried to resume a half-finished delivery, because it depended on what a Chatwoot message window can show an AgentBot (two messages; a newer message hides an older one). Each fix exposed the next hole.
- **Customer-visible cost: a delivery interrupted by a crash or a lease expiry gets no delayed automatic answer. A person must answer it. How often that happens is unmeasured.**
- What the sweeper does with a delivery whose lease expired (`src/recovery.ts`, `src/recovery-escalation.ts`): it takes the lease, then
  1. reads the delivery's action rows from the ledger. If the reply (or a handoff acknowledgement) is a COMPLETED row, nothing else is in flight and this delivery holds no escalation, it is PROVABLY COMPLETE: it is closed with no escalation, no Chatwoot write and no alert. Positive evidence only: a reply row left `in_progress` counts only if the reply is FOUND in Chatwoot; "not found" or "cannot tell" is never evidence of completion.
  2. otherwise, if a person holds the conversation (the ownership store says so, another delivery's escalation holds it, or Chatwoot's own status is not `pending` / it is assigned), the escalation is SUPERSEDED: nothing is written to the conversation and every open action is closed as superseded.
  3. otherwise it records the durable intent (the ownership hold, operation id `escalate:<event>`, idempotent), then leaves the private note, opens the conversation and assigns the team, each under the delivery's ledger claim and write fence. A note that cannot be proven absent is NOT resent. If neither the opening nor the assignment reaches Chatwoot the delivery is left open (and alerted) for the next sweep; the attempt cap (8) bounds that.
  4. closes every action row with a recorded disposition: `completed` (performed) or a failed row whose `failure_code` is `disposition_not_sent_escalated` (not confirmed sent, never resent, a person asked), `disposition_superseded` or `disposition_abandoned`. No schema change: `failure_code` already exists and holds text. Nothing stays `in_progress` beneath a closed delivery.
  5. raises an alert and closes the delivery.
- It NEVER calls the model, sends a customer message, rebuilds the inbound message, or touches a conversation a person already holds. `rebuildPayload`, the resume-after-reply path and `unfinishedAfterReply` were removed.
- **ALERT ROUTE: no person is reached out-of-band today.** The alerts are (a) the private note on the conversation, which is the in-product alert, and (b) a loud ERROR-level log line (event `recovery_escalation`, stable `alertCode`: `recovery_escalated_to_human`, `recovery_escalation_not_visible`, `recovery_abandoned`) through an injectable `AlertSink`. The gateway has no approved out-of-band alert route, and none was invented (no client, no credential). THE MISSING PIECE for a person to be reached out-of-band is an owner decision between: a gateway-dedicated ops webhook / Telegram bot token placed value-blind as a Swarm secret, or an existing monitor that reads the structured log event. Until then a person finds these through the Chatwoot inbox (the conversation is opened) or by someone watching the log.
- KNOWN LIMIT: a reply that promised a colleague whose hold was never recorded leaves no durable trace of the promise (the reply text is not stored), so recovery cannot tell it from a plain reply and treats it as complete.

## Open: exclusive execution (Codex round 3 F2 + F3) - NOT fixed here
The turn budget (R2 design below) is USEFUL CONTAINMENT. It is NOT a proof that worker A stops acting before worker B starts, and an earlier version of this file said it was. Codex (round 3) demonstrated:
- F2 (P1): `finish()` checks the deadline BEFORE awaiting `ledger.complete()`, and the SQL carries no owner / lease predicate, so A's delayed completion can close B's row. Some ownership reads are not raced against the budget; `HUMAN_REQUESTED` can be recorded after the deadline; the recovery shortcut closes a delivery after its own deadline; action claims and settlements are not bounded by the delivery deadline.
- F3 (P1): reconciliation cannot exclude a still-pending upstream write. A sends at second 269 and aborts; the server keeps the operation; B reconciles `absent` at 301 and sends; A's write commits at 320: TWO customer messages. A fixed margin cannot establish this.
Direction (Lane A): do NOT add more timing machinery. These need a fenced lease (a lease token or fencing counter compared in the SQL predicate of every durable write and `complete()`) and an idempotency / reconciliation key that survives a late commit. That is a schema + code change to a deployed service and needs owner authorisation: see `drafts/PIVOT-FENCED-LEASES-DESIGN-PROPOSAL-2026-10-03.md` and the one-page owner explanation. Nothing is applied.

### R2 design: the turn budget (containment, NOT exclusivity)
- `GATEWAY_TURN_BUDGET_MS` (default: the ledger lease minus `TURN_LEASE_MARGIN_MS` = 30 s). Boot REFUSES unless `budget + margin <= lease` and the runtime timeout, the Chatwoot timeout and (when enabled) Paperclip's deadline and request timeout are each inside the budget.
- What it enforces, measured from when the turn started: every Chatwoot request, body read included, is aborted at the turn deadline and is never sent once the budget is spent; the runtime call is raced against it and receives the abort signal; the write fence (asked before every wire write) refuses at/after it; `escalate()` declines to record its hold after it; and `finish()` does not complete the row after it.
- What it does NOT enforce (and earlier versions of this note overclaimed): the handoff path records its ownership hold WITHOUT a deadline check; a durable write already in flight at the deadline can still commit; `ledger.complete()` carries no owner or lease predicate, so the deadline check precedes an awaited SQL that has no lease predicate. It is therefore NOT a proof that no durable mutation starts after the deadline.
- Why heartbeat renewal was not used: it needs a lease-token column and a fenced `complete()` (a schema change). Round 3 shows the budget alone is not enough either; that is the open fenced-lease proposal above.
- Limits that remain: a write already on the wire at the deadline can still commit (F3); timers cannot preempt an event-loop stall; lease and clock behaviour on real PostgreSQL is NOT exercised (the FakeLedger models it); the delivery heartbeat is not renewed by any production caller.

## Known limits (stated, not hidden)
- D8, INHERITED, NOT FIXED: a `pending` Chatwoot status snapshot is treated as proof of an explicit handback (`src/handback.ts`, the manual branch). During escalation the conversation is `pending` before Chatwoot is opened, so that snapshot can be read as a human's gesture and start a handback even with idle handback off. It predates this branch and needs "evidence of an explicit transition for the relevant episode", not a one-line change. So the "explicit-only handback" claim is limited by this. Codex accepts it as acceptable-with-flag and non-gating.
- LOST UNCERTAINTY MARKER ON RESTART - A KNOWN, UNPROVEN RECOVERY. The `IssueStore` (issue ids, run ids AND the "uncertain create" marker) is in process memory (and another replica does not share it). After a restart an uncertain create is no longer remembered and is not re-detected; recovery then rests entirely on Paperclip honouring the same `idempotencyKey` (UNVERIFIED). Sequential replay in one process is tested; restart recovery is not.
- "FAIL-CLOSED DEFAULT" FOR CUSTOMER SCOPE DOES NOT MEAN ENABLED BY DEFAULT. `GATEWAY_CUSTOMER_SCOPE_MODE` unset (or `off`) = NO resolver is consulted and behaviour is exactly what it was: there is NO scope gate. `fail_closed` and `fixture` are opt-in. With scope mode off, none of the customer-scope protection exists.
- OWNERSHIP IS NOT ATOMIC WITH THE WRITES, AND THE WINDOW IS NOT "ONE ROUND TRIP". A reply plus its annotations is up to five HTTP operations and an escalation up to seven. The fence is asked immediately before each write, so a takeover is caught at the next write boundary. What no re-read can remove is the final read-to-send interval of the ONE write already in flight (a reply that was already being posted when a person took the conversation still lands).
- A write the fence denies is released with `ledger.release()` when the turn budget caused the denial (retryable, F4) and closed with `ledger.fail(.., "fenced")` when a person took the conversation (terminal suppression). `fail()` is NOT a "release": it is terminal. If either call fails, the claim stays and a later attempt treats it as claimed-and-unrecorded (reconcile, never blind resend).
- An escalation that finds the conversation in a NEWER ownership episode makes no writes at all, when the precondition is evaluated on a fresh transition (F5) and, since G4-2, on a replay as well. It is still not atomic with the Chatwoot writes that follow, and the customer may have received the runtime's reply text without any escalation having been recorded.
- The route tests for the Paperclip path inject a constructed router; only the D3 test goes through the real `createGateway` assembly.
- The repository tests mostly assert `bootErrors()` return values rather than launching the process to prove `process.exit(1)`; Codex confirmed the exit mechanism with isolated launches.
- Redirects are refused for EVERY outbound call through the egress guard, including Chatwoot and the runtime. A deployment that depended on a redirect (an http->https upgrade, a moved host) will now fail closed with an egress block. None was found in this repository.
- The egress allowlist is hostnames only, not ports.
- RECOVERY COMPLETION IS STILL UNFENCED (F2): the sweeper's `complete()` and `fail()` carry no owner or lease predicate, exactly like the live path. The recovery rule makes recovery do less and record more; it does not make recovery exclusive. A live handler can overlap a recovery handler after the lease expires.
- RECOVERY SUPERSESSION: when a delivery's escalation was unpublished and a person has since taken the conversation (or it was handed back, or Chatwoot shows it open / assigned), recovery does NOT publish the note, status change or assignment, and closes the delivery with the open actions recorded `disposition_superseded`. The context note a colleague would have read is therefore never posted in that case. That is deliberate (re-opening a conversation a person holds would take it from them), and a behaviour choice that Codex or the owner may want to reverse. It is RECORDED, no longer left `in_progress`.
- Ledger claim ownership (`owned`) describes who holds a claim's lease; it does not make execution exclusive. A claim held under a live lease by another worker is still reconciled and, if absent, sent (F3).
- Recovery's own alert reaches nobody out-of-band (see the alert route above).
