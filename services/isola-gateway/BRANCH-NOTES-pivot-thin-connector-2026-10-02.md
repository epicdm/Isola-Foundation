## Open: exclusive execution (Codex round 3 F2 + F3) - NOT fixed here
The turn budget (R2 design below) is USEFUL CONTAINMENT. It is NOT a proof that worker A stops acting before worker B starts, and an earlier version of this file said it was. Codex (round 3) demonstrated:
- F2 (P1): `finish()` checks the deadline BEFORE awaiting `ledger.complete()`, and the SQL carries no owner / lease predicate, so A's delayed completion can close B's row. Some ownership reads are not raced against the budget; `HUMAN_REQUESTED` can be recorded after the deadline; the recovery shortcut closes a delivery after its own deadline; action claims and settlements are not bounded by the delivery deadline.
- F3 (P1): reconciliation cannot exclude a still-pending upstream write. A sends at second 269 and aborts; the server keeps the operation; B reconciles `absent` at 301 and sends; A's write commits at 320: TWO customer messages. A fixed margin cannot establish this.
Direction (Lane A): do NOT add more timing machinery. These need a fenced lease (a lease token or fencing counter compared in the SQL predicate of every durable write and `complete()`) and an idempotency / reconciliation key that survives a late commit. That is a schema + code change to a deployed service and needs owner authorisation: a SEPARATE design proposal is being written. Nothing is applied.

### R2 design: the turn budget (containment, NOT exclusivity)
- `GATEWAY_TURN_BUDGET_MS` (default: the ledger lease minus `TURN_LEASE_MARGIN_MS` = 30 s). Boot REFUSES unless `budget + margin <= lease` and the runtime timeout, the Chatwoot timeout and (when enabled) Paperclip's deadline and request timeout are each inside the budget.
- Enforcement, measured from when the turn started: every Chatwoot request, body read included, is aborted at the turn deadline and is never sent once the budget is spent; the runtime call is raced against it AND now receives the abort signal (F1); the write fence (asked before every wire write) refuses at/after it; the escalation path declines to record its hold after it (Codex's independent expired-handoff probe still recorded `HUMAN_REQUESTED` after the budget on the handoff path: F2, open); and the delivery row is not completed after the deadline CHECK (but see F2: the check precedes the awaited SQL, which has no lease predicate).
- Why heartbeat renewal was not used: it needs a lease-token column and a fenced `complete()` (a schema change). Round 3 shows the budget alone is not enough either; that is the open fenced-lease proposal above.
- Limits that remain: a write already on the wire at the deadline can still commit (F3); timers cannot preempt an event-loop stall; lease and clock behaviour on real PostgreSQL is NOT exercised (the FakeLedger models it); the delivery heartbeat is not renewed by any production caller.

## Known limits (stated, not hidden)
- D8, INHERITED, NOT FIXED: a `pending` Chatwoot status snapshot is treated as proof of an explicit handback (`src/handback.ts`, the manual branch). During escalation the conversation is `pending` before Chatwoot is opened, so that snapshot can be read as a human's gesture and start a handback even with idle handback off. It predates this branch and needs "evidence of an explicit transition for the relevant episode", not a one-line change. So the "explicit-only handback" claim is limited by this. Codex accepts it as acceptable-with-flag and non-gating.
- LOST UNCERTAINTY MARKER ON RESTART - A KNOWN, UNPROVEN RECOVERY. The `IssueStore` (issue ids, run ids AND the "uncertain create" marker) is in process memory (and another replica does not share it). After a restart an uncertain create is no longer remembered and is not re-detected; recovery then rests entirely on Paperclip honouring the same `idempotencyKey` (UNVERIFIED). Sequential replay in one process is tested; restart recovery is not.
- "FAIL-CLOSED DEFAULT" FOR CUSTOMER SCOPE DOES NOT MEAN ENABLED BY DEFAULT. `GATEWAY_CUSTOMER_SCOPE_MODE` unset (or `off`) = NO resolver is consulted and behaviour is exactly what it was: there is NO scope gate. `fail_closed` and `fixture` are opt-in. With scope mode off, none of the customer-scope protection exists.
- OWNERSHIP IS NOT ATOMIC WITH THE WRITES, AND THE WINDOW IS NOT "ONE ROUND TRIP". A reply plus its annotations is up to five HTTP operations and an escalation up to seven. The fence is asked immediately before each write, so a takeover is caught at the next write boundary. What no re-read can remove is the final read-to-send interval of the ONE write already in flight (a reply that was already being posted when a person took the conversation still lands).
- A write the fence denies is released with `ledger.release()` when the turn budget caused the denial (retryable, F4) and closed with `ledger.fail(.., "fenced")` when a person took the conversation (terminal suppression). `fail()` is NOT a "release": it is terminal. If either call fails, the claim stays and a later attempt treats it as claimed-and-unrecorded (reconcile, never blind resend).
- An escalation that finds the conversation in a NEWER ownership episode makes no writes at all, when the precondition is evaluated on a fresh transition (F5) and, since G4-2, on a replay as well. It is still not atomic with the Chatwoot writes that follow, and the customer may have received the runtime's reply text without any escalation having been recorded.
- The route tests for the Paperclip path inject a constructed router; only the D3 test goes through the real `createGateway` assembly.
- The repository tests mostly assert `bootErrors()` return values rather than launching the process to prove `process.exit(1)`; Codex confirmed the exit mechanism with isolated launches.
- Redirects are refused for EVERY outbound call through the egress guard, including Chatwoot and the runtime. A deployment that depended on a redirect (an http->https upgrade, a moved host) will now fail closed with an egress block. None was found in this repository.
- The egress allowlist is hostnames only, not ports.
- RECOVERY COMPLETION IS STILL UNFENCED (F2): the sweeper's `complete()` carries no owner or lease predicate, exactly like the live path. G4-1 only makes recovery finish what the delivery began; it does not make recovery exclusive.
- G4-1 SUPERSESSION: when a delivery's escalation was released and a person has since taken the conversation (or it was handed back), recovery does NOT publish the note, status change or assignment, and closes the delivery. The context note a colleague would have read is therefore never posted in that case. That is deliberate (re-opening a conversation a person holds would take it from them), and it is a behaviour choice that Codex or the owner may want to reverse.
- An unsettled escalation action whose hold is NOT this delivery's is never retried, so its row stays `in_progress` forever; it is invisible to the sweeper (which selects delivery rows).
- Ledger claim ownership (`owned`) describes who holds a claim's lease; it does not make execution exclusive. A claim held under a live lease by another worker is still reconciled and, if absent, sent (F3).
